# Goodgorithm — project context

Read this before starting work. It's the condensed version of decisions made in planning and in code. Deeper public-facing mechanism/policy docs live on the GitHub Wiki (see Docs at the bottom); Notion is internal-only historical archive now, not a primary reference.

## What this is

An open-source, free-forever, ad-free algorithmic feed of positive/uplifting public social posts. The pitch: counter the negativity bias of mainstream platform algorithms, and reclaim "algorithm" from its usual "platform manipulating you" connotation.

**Status:** early development. `ingestion/`, `processing/`, and `api/` run on Railway; `web/` (PWA + Capacitor native) deploys to Cloudflare Workers. All four are live in both `staging` and `production`. Production: [goodgorithm.com](https://goodgorithm.com). Staging: [goodgorithm-web-staging.bandza88.workers.dev](https://goodgorithm-web-staging.bandza88.workers.dev/).

## Three constraints that are load-bearing, not aspirational

**1. No LLM in the algorithm itself.** Content selection (sentiment scoring, topic/newsworthiness detection, ranking) runs on classic ML: TF-IDF, spaCy NER, MinHash/LSH, a small CNN over word embeddings for sentiment. Not an LLM. The reasoning: the whole pitch is "trust why a post got selected," and classical ML is small, auditable, and doesn't drift or hallucinate the way an LLM can. This is specifically about what powers the algorithm — it does not extend to how the project is built. LLM tools (including Claude) are used openly for development, research, and docs. Don't blur this distinction in code comments, docs, or commit messages: "no LLMs in the filter," not "no LLMs anywhere."

**2. No engagement signals in ranking.** The ranking/dedup pipeline must never read likes, reposts, replies, or follower counts from the source platform. An earlier draft violated this (used an HN-style upvote-decay formula) before being caught and rewritten — a concrete reminder this constraint needs active enforcement, not just a policy statement. `processing/src/pipeline_stages/ranking.py`'s `compute_base_score` is the literal enforcement of this: `positivity(sentiment) × topicality × recency_decay`, no other fields exist on `RankablePost` for this to accidentally read. Bot-filtering (`bot_filter.py`) is allowed but stays defensive-only — a hard eligibility filter, never a score boost, so it can't become a backdoor engagement signal.

**3. No attention-optimization in the product.** No streaks, no "come back" push notifications, no autoplay-next, nothing engineered to maximize time-in-app. The natural extension of the other two: the product isn't just neutral about engagement, it's actively fine with not holding you, because the point is inspiring real-world action, not screen time. Unlike constraints 1 and 2, there's no single code path enforcing this today — it's a review criterion for future feature work (anti-repeat's cursor persistence, for example, was checked against it: purely a "don't lose your place" convenience, no re-engagement mechanic attached), not a retrofit of something already built.

## Architecture (as built)

Five services, each independently deployable:

| Path | Language | Deployed as | What it does |
|---|---|---|---|
| `ingestion/` | TypeScript | Railway service `goodgorithm-ingestion` | Long-lived process: Bluesky Jetstream WebSocket + Mastodon polling → `raw_posts` in Postgres. |
| `processing/` | Python | Railway service `goodgorithm-processing` | Long-lived loop: content filter → dedup → bot filter → topicality → quote resolution → sentiment → base score → MMR ranking → `processed_posts`. |
| `api/` | TypeScript (Fastify) | Railway service `goodgorithm-api` | Stateless, read-only, unauthenticated HTTP — no outbound calls of its own (see Post attachments & embeds below). `/feed` (cursor-paginated, ordered by `rank_score`), `/health`. |
| `web/` | TypeScript (React + Vite) | Cloudflare Workers static assets (`goodgorithm-web`, staging/production named environments) | PWA *and* Capacitor-wrapped native iOS/Android app, same codebase: infinite-scroll feed consuming `api/`'s `/feed`, no accounts/personalization. `VITE_API_BASE_URL` baked in at build time (static site, no server component). |
| `training/` | Python (notebook) | Run manually on Colab/Kaggle, not deployed | Trains the sentiment CNN, exports to ONNX, publishes versioned artifacts to R2. |

Schema lives in `supabase/migrations/` (`raw_posts`, `processed_posts`, applied via Supabase's migration tooling — don't hand-edit the schema elsewhere).

**For the exact step-by-step mechanics of every pipeline stage** (thresholds, formulas, why each one works the way it does), see the published **Algorithm** page on the GitHub Wiki (see Docs at the bottom for the link) — that's the canonical, kept-current explanation. Don't duplicate it at length here; it'll drift.

### Data flow

```
Bluesky Jetstream ─┐
                    ├─> ingestion/ ─> raw_posts ─> processing/ ─> processed_posts ─> api/ ─> /feed ─> web/
Mastodon polling ───┘                  (dedup, bot filter, topicality,
                                         sentiment, base score, MMR rank)
```

`raw_posts` and `processed_posts` are separate tables, joined at read time — nothing is ever mutated in `raw_posts` after ingestion, so the original data is always intact for audit/replay even as scoring logic evolves.

### Sentiment model loading

`processing/` tries once per process to load the trained CNN from R2 (`sentiment-cnn/latest.json` → versioned `model.onnx`/`vocab.json`/`config.json`); on any failure (R2 not configured, network error, nothing published yet) it falls back to VADER and keeps running. `sentiment_method` on every scored post records which one actually produced that score. To train and publish a new model version, use the `release-sentiment-model` skill (`.claude/skills/release-sentiment-model/`) rather than improvising the R2 upload — it covers the tokenizer commit-pinning requirement and the versioned/gated-promotion release process.

### Data retention

Alpha-stage cap, not a correctness requirement: both Postgres and Redis only retain the last 24 hours of data. `processing/src/pipeline.py`'s `RETENTION_HOURS` (env-configurable, default `24`) drives a `cleanup_old_data()` step that runs every cycle, deleting `raw_posts` older than the cutoff; `processed_posts` rows cascade-delete via FK (`supabase/migrations/0003_cascade_delete_processed_posts.sql`). Redis TTLs for dedup (`DEDUP_BAND_TTL_SECONDS`, `dedup.py`) and bot-filter self-dup tracking (`SELF_DUP_TTL_SECONDS`, `bot_filter.py`) are aligned to the same 24h window — no point holding LSH/dedup state for posts that no longer exist in Postgres. `pipeline.py` checks `DEDUP_BAND_TTL_SECONDS >= RETENTION_HOURS * 3600` at startup and refuses to start otherwise — dedup state expiring before its posts do would silently let real near-duplicates back into the feed.

Note `ranking.py`'s `RANKING_MMR_WINDOW_HOURS` (env-configurable, default `72.0`) is still `72.0` by default but is now effectively capped at 24h by retention (a post can't survive long enough to hit the 72h boundary) — left as-is rather than changed, so it becomes meaningful again automatically if retention is raised post-alpha. Don't "fix" this mismatch without understanding why it's there first.

Migration 0003 has been applied and the retention code deployed on both `staging` and `production`. As with any infra/deploy state, check actual state (`git log`, Supabase migration list, Railway deploy status) before assuming this file is current — code/infra changes happen via Claude Code across many sessions, so this file can lag reality between doc syncs.

### Post attachments & embeds

`api/src/attachments.ts` parses each post's images, link cards, video, and quote-post content into a normalized `Attachment[]` the frontend renders — the `Attachment` union is hand-duplicated in `web/src/api/types.ts` (no shared package across the API/web boundary in this repo). Images and link cards are pure string-templating off `raw_json` (Bluesky's CDN URLs, Mastodon's own media URLs) with zero network calls at serve time.

Video follows the same pure-templating pattern: Bluesky's raw video embed only has a blob ref (CID), but the HLS playlist URL is deterministically constructable client-side as `https://video.bsky.app/watch/{did}/{videoCid}/playlist.m3u8` — no AppView call, `api/` stays untouched architecturally. Mastodon's `video`/`gifv` media are already-playable URLs. `web/`'s `VideoPlayer.tsx` uses `hls.js` as a non-Safari fallback for the `.m3u8` URLs (native `<video>` handles Mastodon's plain MP4s and Safari's native HLS directly); GIF-like video (Bluesky `presentation: "gif"`, Mastodon `gifv`) autoplays muted/looping/no-controls, regular video requires a tap.

Quote-post content resolution is the one piece that isn't pure templating — a Bluesky quote embed only ever carries `{cid, uri}`, so showing the quoted post's own text/author needs a live call to Bluesky's public, unauthenticated AppView (`app.bsky.feed.getPosts`, batched up to 25 URIs/call). This resolution happens in `processing/src/pipeline_stages/quote_resolver.py` at scoring time, not in `api/` — `processing/`'s first outbound network dependency, deliberately placed there rather than in `api/` so `api/` stays stateless/DB-in-JSON-out, and so quoted content can be run through the same `content_filter.is_content_excluded()` checks a regular post gets before it's ever stored (a quoted post carries its own moderation status independent of the post quoting it). The result is a pre-shaped, already-filtered blob on a nullable `processed_posts.quote_content` column that `api/` passes straight through with no further shaping. Deliberately never reads or stores the engagement counts (`likeCount`/`repostCount`/etc.) that `getPosts`' response includes — no engagement signals anywhere in the product, not just ranking. A quoted post absent from a successful response (deleted/blocked/detached — `getPosts` doesn't distinguish which) resolves to an explicit `not_found` status; a network/API failure just leaves `quote_content` null for that post, with no retry, since each `raw_post` is only ever scored once.

### Category filtering

`processing/src/pipeline_stages/category_model.py` assigns each post one of four categories: **science_technology, arts_culture, food_dining, diaries_daily_life**. A trained TF-IDF + one-vs-rest logistic regression classifier (classical ML per the no-LLM-in-the-algorithm constraint, same as the sentiment CNN) is the primary mechanism, trained on a trimmed subset of `cardiffnlp/tweet_topic_multi` (HuggingFace — the same CardiffNLP research group behind `tweet_eval`, which the sentiment model already trains on). `taxonomy.py`'s keyword/phrase matcher is the whole-process fallback for when the classifier can't load, gated the same way `sentiment.py` falls back to VADER (`category_model.CATEGORY_METHOD`, recorded per-post on `processed_posts.category_method`). Once loaded, the trained model's output is used as-is — never second-guessed on a per-post basis, the same trust level as the sentiment CNN.

The category set replaced an earlier rule/keyword-only 8-category set (Technology, Arts & Culture, Animals, Science & Discovery, Kindness & Community, Environment & Nature, Health & Recovery, Sports & Achievement) that had a hard recall ceiling from exact-keyword matching alone — too few posts got categorized at all. The trained classifier's original 8 (an intermediate step, not this one) were sourced from what `tweet_topic_multi` actually supports rather than a forced rename of the originals — `animals`, `kindness_community`, and `environment_nature` were dropped entirely (no equivalent in that dataset, and near-zero volume via keyword-only matching wasn't worth keeping alive). `web/`'s default category (`arts_culture`) replaced the original `kindness_community` default for the same reason — closest in spirit (broadly appealing, not niche) among what's left, and happens to be the highest-volume category too, both then and now.

**Narrowed from 8 to 4 (`sports`, `health_fitness`, `learning_education`, `travel_adventure` dropped) once real production data existed to check against ([issue #37](https://github.com/goodgorithm/goodgorithm/issues/37); [issue #54](https://github.com/goodgorithm/goodgorithm/issues/54) — `health_fitness`'s specific mistagging problem — is resolved by this rather than fixed in place).** The offline per-label eval that shipped with the original 8 showed a sharp divide (`arts_culture`/`sports` at 0.84–0.86 F1, everything else 0.09–0.47) but explicitly wasn't trusted as the final word — issue #37 asked for real production feedback first. That feedback: 20–37 real live posts sampled per category directly against production and hand-judged on-topic/off-topic gave `food_dining` ~95%, `gaming` ~82%, `arts_culture` ~80%, `science_technology` ~60%, `sports` ~52%, `travel_adventure` ~43%, `learning_education` ~28%, `health_fitness` ~23% — a materially different ranking than the offline eval predicted. Two corrections the offline numbers got wrong: `food_dining` and `gaming` were real standouts despite weak offline scores (their offline per-label support was tiny — 15 and 77 examples — so those numbers were never reliable); `sports`, the offline eval's *best*-scoring category, turned out weakest of the four "obviously fine" ones in practice, via a specific, repeatable failure mode invisible in the offline eval's more curated corpus — general "game"-keyword bleed from video-game posts, plus political/news noise. Retraining `category_classifier.ipynb` on just the 4 kept labels also required re-picking `CONFIDENCE_THRESHOLD` from scratch rather than carrying over the prior ~0.55 — fewer competing classes shifts the softmax distribution shape entirely; the new knee is ~0.65, where deployed-policy accuracy and off-taxonomy-abstain-correctness both improve together, not a tradeoff.

**`gaming` was later swapped for `diaries_daily_life` ([issue #62](https://github.com/goodgorithm/goodgorithm/issues/62), following [issue #61](https://github.com/goodgorithm/goodgorithm/issues/61)'s investigation).** #61 set out to measure category correlation (prompted by sports content visibly bleeding into `gaming`) and, along the way, did a from-scratch review of all 19 `tweet_topic_multi` labels without anchoring to the original 8 concepts the taxonomy had been scoped around at every prior pass. `diaries_&_daily_life` had never been considered at any point in the taxonomy's history for exactly that reason — it doesn't map onto any of the original 8 ideas — but turned out to be the strongest unexplored category: real production precision was strong once split by ranking eligibility, and estimated volume (~2–3% of all traffic) rivalled every category except `arts_culture`. `gaming` was retired rather than kept alongside it, since it was also the category at the center of #61's original motivating problem — removing it resolves the sports-bleed confusion directly. Retraining required its own fresh `CONFIDENCE_THRESHOLD` sweep rather than carrying over the prior 0.65 (same lesson as the 8→4 narrowing) — it happened to land on 0.65 again, confirmed as the genuine sweep knee for this label set, not assumed. `diaries_daily_life`'s training support (731 examples) is the second-largest of the 4, behind only `arts_culture`'s 1,477.

Training/release infrastructure mirrors the sentiment CNN's exactly, generalized rather than forked (`training/r2_release.py` takes a `--model {sentiment,category}` flag; `model_store.py`'s `R2ModelStore` takes a `prefix` arg) — see the `release-category-classifier` skill. Unlike the sentiment notebook, `category_classifier.ipynb` doesn't need a GPU.

`category` is **deliberately not threaded into `ranking.py`/`RankablePost`** — a post-hoc filter on top of the existing `rank_score`, not a ranking input (same "don't accidentally create a backdoor scoring signal" discipline as the two load-bearing constraints above). `api/`'s `/feed` validates `?category=` against `api/src/types.ts`'s `CATEGORIES`; `web/`'s `CategorySelector` renders all four as a no-scroll, always-fully-visible grid — needed no code change for the narrowing, since the grid was already `auto-fill`/`minmax`-based with no hardcoded category count. The "Full feed"/no-filter option was removed once every category had real volume — an unfiltered feed no longer earned the risk it carried, and `category` is now non-nullable end to end in `web/` as a result.

### Non-English content filtering

Closes a gap in the "English-only on both paths" claim below (Data sources): `ingestion/`'s language filters (`bluesky.ts`'s self-reported `langs` tag, `mastodon.ts`'s server-detected `language` field) only exclude a post when a *non*-English tag is present — an absent tag was treated as English by default, which real production sampling showed was wrong often enough to matter.

`processing/src/pipeline_stages/language_filter.py` closes this with fastText's `lid.176` pretrained language-ID model (176 languages, Meta's official release), chosen over `lingua-py` after benchmarking both against real production text — fastText had a meaningfully lower false-positive rate on confirmed-English posts at equal recall on confirmed non-English text. Runs on posts with no language tag at all (`pipeline.py`'s `run_cycle`, same hard-exclude gate as `content_filter.py` and the moderation blocklist), at a tuned confidence threshold so low-confidence guesses on short/ambiguous text don't cause false exclusions — an inconclusive read is kept, not excluded, matching `bot_filter.py`'s "don't exclude on a weak signal alone" caution. The model itself isn't committed to the repo (this project's `.gitignore` convention for ML artifacts) — fetched once per process from Meta's stable public CDN and cached locally, mirroring the pinned-third-party-artifact-URL pattern `pyproject.toml` already uses for `en_core_web_sm`.

**Also runs on every Mastodon post regardless of its tag, not just untagged ones** — a *tagged* post used to skip fastText verification entirely on the assumption a source-reported tag can be trusted, but Mastodon's server-reported language can be wrong at a real, meaningful rate (an automated posting tool defaulting to "English" regardless of actual content was one confirmed case), not concentrated only in bot accounts. **Deliberately not extended to Bluesky's tagged posts** — real testing found a meaningful share of Bluesky "mistags" were fastText false positives on short, casual English text, since Bluesky's `langs` is the poster's own client-set self-report with no analogous wrong-by-default mechanism the way an automated Mastodon posting tool has. Extending verification there would trade a small, mostly-illusory gap for a real new false-exclusion problem.

### Content moderation

Two independent hard-exclude mechanisms run in `pipeline.py`'s `run_cycle`, both checked before dedup/bot/topicality ever run so excluded content never spends that compute or gets a `processed_posts` row: the `blocked_authors` table (a manually-entered or Bluesky-bot-label-auto-inserted `(source, author_id)`, purged retroactively too) and `content_filter.is_content_excluded` (hashtag/self-label/spoiler-text/domain checks on the post itself).

**`suppressed_terms`** replaced `content_filter.py`'s old hardcoded `EXCLUDED_HASHTAGS` frozenset, which had turned out too narrow to catch real adult-content posts self-tagged with anything other than its one hardcoded value. Same pattern as `blocked_authors`: a DB table, loaded whole and fresh once per processing cycle (`db.fetch_suppressed_terms`), so a moderator can add or remove a term without a code change or service restart — today, by hand via the Supabase SQL editor, no admin UI/CLI, same as `blocked_authors`. Deliberately narrow and hand-curated, "precision over recall": only terms that function as an unambiguous adult-content self-tag, not identity/topic terms that merely correlate with it in some posts. Checked against post-body hashtags (`has_excluded_hashtag`) and Mastodon's `spoiler_text` field (`has_excluded_spoiler_text`) — the free-text content-warning label a poster writes (e.g. "NSFW"), just as deliberate a self-tag as a hashtag but not hashtag-formatted, so matched as whole words rather than via the hashtag regex. `quote_resolver.py`'s quoted-post filtering takes the same `suppressed_terms` set, so a quoted post gets identical treatment to a regular one.

**`suppressed_domains`** (issue #57) closes a gap the term/hashtag mechanism was never meant to catch: marketing/affiliate content (Etsy shop listings, Amazon affiliate links) that isn't self-tagged with anything at all — it passes on its own enthusiastic sentiment, the same signal genuine positivity scores on. Same DB-table, loaded-fresh-per-cycle, moderator-edited-by-hand pattern as `suppressed_terms` (`db.fetch_suppressed_domains`), seeded narrow (`amazon.com`, `amzn.to`, `etsy.com` — a real production sample came back 20/20 genuine marketing with zero false positives at that scope). `content_filter.has_excluded_domain` extracts a post's link via `util/url_extract.py`'s `extract_raw_url` (the same Bluesky-embed/Mastodon-card/text-regex extraction `dedup.py`'s `extract_dedup_url` uses, promoted into `util/` so both pipeline stages can share it without one reaching into the other's internals) and matches a listed domain exactly or as a subdomain — deliberately not reusing `extract_dedup_url` itself, since that rejects bare-domain URLs (right for dedup, wrong here: a bare marketplace homepage link should still match). `quote_resolver.py`'s quoted-post filtering takes `suppressed_domains` the same way it already takes `suppressed_terms`.

`ADULT_LABEL_VALUES` (Bluesky's own fixed moderation-service vocabulary for adult content, `com.atproto.label.defs`) stays hardcoded, not DB-driven — it's an external protocol constant Bluesky itself defines, not something a moderator curates.

Mastodon's `sensitive` boolean (self-reported, used today only by `api/src/attachments.ts` for client-side image blurring) is deliberately **not** part of any hard-exclude check — it's a blunt single flag covering nudity, gore, spoilers, and violence alike, not adult-content-specific.

**`ingestion/src/blueskyLabels.ts`** is a second, separate real-time mechanism, distinct from everything above: a standing WebSocket subscription to Bluesky's own moderation-labeler stream (`com.atproto.label.subscribeLabels`), independent of the Jetstream firehose connection. On an `ADULT_LABEL_VALUES` match it retroactively deletes the already-ingested `raw_posts` row (`deleteBySourceId`); on Bluesky's own `"bot"` account-level label it retroactively blocks the author (`blockAuthor`, picked up by `purge_blocked_authors()`). This exists because Bluesky's own automated image-scanning judgment on a post's actual content arrives asynchronously, a few seconds after post creation — later than Jetstream's post-create event, so it can never be caught by any of the ingestion-time/scoring-time checks above.

**Two real nudity posts made it into the feed anyway (issue #67) — not because this mechanism was missing, but a genuine race condition in it.** `bluesky.ts`'s Jetstream-driven `INSERT` and `blueskyLabels.ts`'s label-driven `DELETE` are two independent WebSocket connections in the same process with no coordination between them. Confirmed directly in both incidents via Railway logs: the label arrived and `deleteBySourceId` ran *before* the corresponding `INSERT` had landed (a 4-8s gap, faster than that particular post's ingestion latency that time) — the delete found nothing, and since it was a one-shot attempt with no retry, the post survived once the insert completed moments later. Fixed with `ingestion/src/pendingExclusions.ts`, a small in-memory, TTL-bounded (`BLUESKY_PENDING_EXCLUSION_TTL_MS`, default 30s) map shared between the two files: a delete-miss records the `sourceId` as pending; `bluesky.ts` checks it right before every insert and skips if found. No new DB table or retry loop — the common case (post never ingested at all, `BLUESKY_SAMPLE_RATE` means most real-time adult labels aren't ours) costs nothing, and the rare real race is closed deterministically at the exact moment of insert rather than via a guessed retry delay.

**A second, independent backstop was added in `processing/`** (`pipeline_stages/moderation_recheck.py`, wired as `pipeline.recheck_moderation()`), on the reasoning that a single real-time listener with in-memory state is a single point of failure for a content-safety mechanism (a `blueskyLabels.ts` WS disconnect gap, an `ingestion` process restart losing the pending-exclusion map, etc.). Mirrors `quote_resolver.py`'s exact `getPosts`-batching pattern, but decoupled from ingestion time (a throttled sweep over already-scored posts, not inline in `run_cycle`, since `run_cycle` can pick up a row within seconds of ingestion — the same race window, not a genuinely independent check). Checks both `postView.labels` (the post's own current moderation labels, redundant with but independent of the real-time listener) and `postView.author.labels` (the author's profile-level self-label — a separate, smaller, previously-unchecked-anywhere gap, closed for free since `getPosts` already returns it). Tracked via `processed_posts.moderation_checked_at` (nullable, additive, migration `0015`) so each post is swept exactly once. Deliberately throttled (`MODERATION_RECHECK_INTERVAL_SECONDS`, default 10s) rather than unthrottled like `purge_blocked_authors()` — this one calls an external API in batches, and running it unthrottled under a large backlog would compound exactly like the unthrottled MMR pass did before the Performance & staging cost work below, or like the Redis capacity incident further down this file. Still comfortably beats the 30s `refresh_rankings` floor that actually gates a post becoming feed-visible.

## Performance & staging cost

Prompted by staging running `ingestion`/`processing` at full production intensity for no functional need, plus a general look for performance issues missed while heads-down on functionality. The single biggest lever, `refresh_rankings()`'s MMR pass rerunning its full O(n²) similarity computation nearly every loop iteration, cost **both** environments, not just staging — so most of this pass is a general perf fix, not a staging-only one.

- `processing/src/main.py`: `refresh_rankings()` is now throttled to a configurable minimum cadence (`REFRESH_RANKINGS_INTERVAL_SECONDS`, default `30`) instead of running unconditionally every loop iteration; the backlog-aware loop's sleep between iterations is now `PROCESSING_BACKLOG_BUFFER_SECONDS` (default `3`, preserving prior behavior) instead of a hardcoded constant.
- `processing/src/pipeline_stages/topicality.py`: spaCy loads with `parser`/`tagger`/`attribute_ruler` disabled alongside the existing `lemmatizer` disable — only `doc.ents` is ever read, so those pipeline components were dead weight run on every post.
- `processing/src/infra/db.py`/`pipeline.py`: `upsert_processed_posts` batches the per-cycle writes into chunked multi-row `INSERT ... VALUES` (mirroring `update_rank_scores`' existing pattern) instead of one round trip per post.
- `web/src/components/PostAttachments.tsx`: `hls.js`/`VideoPlayer` are now `React.lazy`-loaded, since most posts carry no video and even video-bearing ones on Safari don't need `hls.js` at all — cut the main JS bundle from ~746KB to 238KB (gzip 230KB→74.7KB).
- Staging-only Railway config (no code difference, just lower-intensity settings): `BLUESKY_SAMPLE_RATE=0.01` (vs. production's tuned `0.045`), `PROCESSING_BATCH_SIZE=100`, `PROCESSING_INTERVAL_SECONDS=600`. Deliberately not touched: `DISABLE_LABEL_FILTER` (staging keeps validating the full content-safety pipeline) and Mastodon polling config (already negligible volume).

## Redis capacity

Production `processing` once crash-looped on Upstash's "DB capacity quota exceeded" (1GB plan cap, both environments) — tracked as [GitHub issue #1](https://github.com/goodgorithm/goodgorithm/issues/1). Root cause was a specific tradeoff: restoring `dedup.py`'s `NUM_PERM`/`NUM_BANDS` from a cost-optimized 64/8 back to the empirically-verified 128/16 roughly doubles per-post Redis writes, with no corresponding change to the byte cap. Worth remembering if either constant is ever tuned again — check the capacity math, not just the dedup-accuracy tradeoff.

- `processing/src/infra/redis_guard.py` (new): checked once per cycle, before that cycle's dedup/bot-filter/topicality writes (`pipeline.py`'s `enforce_redis_capacity()`, called from `main.py`). Once usage crosses `REDIS_SOFT_LIMIT_RATIO` (env var, default `0.70`) of `REDIS_MAX_BYTES` (config/env var, default `1073741824` = 1GB, matching both environments' current plan), proactively clears expendable data instead of writing blind until Upstash rejects a write and crashes the process. Deliberately never touches dedup's own state (`lsh:band:*`, `mh:*`, `dedup:cluster:*`) — silently losing that would let duplicate content back into the feed unnoticed, a worse failure than the loud crash this guard prevents. Only clears `burst:entity:*` (topicality's explicitly short-lived "spiking now" signal) and `cluster:*:authors` (bot-filter's secondary self-dup signal; `botvel:*` velocity tracking is untouched).
- **The guard's usage estimate was silently blind for its entire existence until [issue #65](https://github.com/goodgorithm/goodgorithm/issues/65).** It originally read Redis's own `INFO memory` `used_memory` figure — confirmed in a real production incident that Upstash's REST API returns wildly inconsistent values for it (three consecutive reads one second apart on the same connection: 47917017, 7572913, 47917017 bytes, with nothing actually changing), completely disconnected from Upstash's own real capacity-quota enforcement. At the exact moment production's writes were being rejected at ~100% of the 1GB cap, the guard's own reading showed 1.9–4.4%, so its 85% soft limit had likely never once fired for real. `estimate_used_memory_bytes()` now estimates total bytes as `DBSIZE * (a fresh sampled average of real MEMORY USAGE reads)` — both confirmed stable/trustworthy during that incident's remediation, unlike `INFO memory`. Deliberately re-sampled every check rather than a hardcoded bytes-per-key constant, since the key-size mix (`mh:*`'s ~700-byte MinHash signatures dominate, but `lsh:band:*`/`dedup:cluster:*`/`dedup:url:*`/`botvel:*`/`cluster:*:authors`/`tmpl:*`/`burst:entity:*` all coexist at very different sizes) can drift as traffic composition or dedup config changes — a stale constant would risk degrading silently the same way `INFO memory` did.
- **The #65 fix's own sample was still too small, caught in a follow-up incident the same day.** After the fix deployed, production hit ~1GB again; `DBSIZE` was back near its pre-incident level (`4,698,860` vs. the original crash's `4,658,608`) while the newly-deployed estimate read only 14.4% — a real, ~7x-too-low miss. Root cause: `REDIS_GUARD_MEMORY_SAMPLE_SIZE`'s original default of `100` was too small a random sample for how skewed the keyspace actually is — `lsh:band:*` alone outnumbered `mh:*` 5.6:1 (611,301 vs. 109,114 keys during the original remediation), and both dedup key types are a small minority of the full keyspace once `botvel:*`/`tmpl:*`/`cluster:*:authors`/`burst:entity:*` are counted, so a 100-key draw could easily land on few or no `mh:*` keys (the heaviest payload type) and badly undercount the true average. Raised to `2000`, kept cheap by pipelining the `MEMORY USAGE` calls into one round trip (same discipline `dedup.py`/`bot_filter.py`/`topicality.py` already use) instead of one call per sampled key. `REDIS_SOFT_LIMIT_RATIO` independently lowered `0.85` → `0.70` as margin against whatever sampling error remains. (Separately: the backlog from the original outage — ~120K unprocessed `raw_posts` spanning a full day — meant Redis was still actively regrowing dedup state when this was diagnosed, not yet at steady state; worth remembering if this pattern recurs after a future outage.)
- Fixed a rolling-TTL bug present in both `dedup.py`'s `lsh:band:*` sets and `bot_filter.py`'s `cluster:{cluster_id}:authors` sets: both re-issued `EXPIRE` on every hit/new-member instead of only when first created, so a sustained duplicate/spam wave — exactly what these two modules exist to catch — could keep either key's 24h TTL rolling forward indefinitely. Now uses `EXPIRE ... NX` (only sets the TTL if the key doesn't already have one), same call count, fixed window instead of rolling.
- `dedup.py`'s `mh:{post_id}` (the largest single per-key payload, written on every processed post) now stores the MinHash signature as base64 of its raw `uint32` bytes instead of a comma-separated decimal string — ~1.3KB down to ~700 bytes, confirmed via `serialize_minhash`/`deserialize_minhash`. `deserialize_minhash` treats any old-format or incompatible-`NUM_PERM` data as "no signature" rather than raising, so the up-to-24h window of still-live old-format keys after this deploys degrades gracefully instead of crashing a cycle (the same defensive pattern any future `NUM_PERM` change should follow).
- `topicality.py`'s `burst:entity:*` key names are now capped at 100 chars (`ENTITY_KEY_MAX_LEN`) — entity text comes straight from spaCy NER with no prior bound, an unbounded-length key pattern.

## Versioning & migration

[GitHub issue #18](https://github.com/goodgorithm/goodgorithm/issues/18): a deliberate, evidence-based answer for every integration point where a future change could break whatever's on the other end, not just the ones that happened to get fixed. Findings came from a full audit (three parallel research passes over the HTTP/API boundary, the data/schema boundary, and deploy/taxonomy/PWA mechanics) before any of this was decided — reread that issue for the raw findings if this section ever needs re-deriving.

**`api/` ↔ `web/` contract.** `/feed` is versioned as `/v1/feed` — decided against the initial call in this same pass ("premature with one first-party consumer"), on the reasoning that adding it now, while it's cheap, beats retrofitting it later once there's real traffic and no natural cutover point. `/health` deliberately stays unversioned — it's an infra-level check (Railway's `healthcheckPath`, Better Stack's external monitor), not part of the data contract this is protecting. The unprefixed `/feed` was kept registered alongside `/v1/feed` for a transition window, as a deploy-safety measure (not a compatibility promise) against `api/`'s and `web/`'s separate, non-atomic CI pipelines — dropped once `web/`'s `/v1/feed`-calling deploy was confirmed live on both staging and production (checked directly against each environment's actual served JS bundle) and nothing else was found depending on the old path. `api/src/app.ts` now registers `feedRoute` once, under `{ prefix: "/v1" }`, only.

What actually keeps `api/`'s and `web/`'s shapes in sync: `api/src/types.ts` is the canonical source for every response shape (`FeedPost`, `Attachment`, `QuoteContent`, `Category`, `HealthResponse`, etc.) — `web/`'s copy (`web/src/api/types.generated.ts`) is generated from it by `scripts/sync-api-types.mjs`, not hand-duplicated. This is deliberately *not* a live shared package (npm workspaces or a `file:` dependency): `api/`'s Railway service has `rootDirectory: "/api"` on the `RAILPACK` builder (confirmed via `get-service-config`), and a live cross-directory dependency was genuinely uncertain to build correctly there — untested infra assumptions aren't worth risking a production build over. The generated file is committed, so neither service's build ever needs to reach outside its own directory; `.github/workflows/ci.yml`'s `web-tests` job fails if someone changes `api/src/types.ts` and forgets to run the sync script. Run it yourself after touching that file: `node scripts/sync-api-types.mjs`. Still no runtime validation at this boundary (`web/src/api/client.ts`'s `getJson` trusts `response.json()` blindly) — the generated-types check is a compile-time guarantee, not a runtime one; adding a schema-validation library was considered and deliberately deferred, not silently skipped, to stay consistent with this project's general dependency-light bias (no router, no markdown lib, hand-rolled solutions preferred throughout `web/`).

**`pipeline_version`.** `processed_posts.pipeline_version` existed as a schema column (`DEFAULT 'v1'`) since the table was created, but was dormant — never written or read by any application code — until this pass. Now: `processing/src/pipeline.py`'s `PIPELINE_VERSION` constant is written on every upsert, and `api/`'s `/feed` response exposes it per-post. Mirrors how `sentiment_method` already records which sentiment scorer (CNN vs VADER) produced a score, at the whole-pipeline level rather than one stage. Bump `PIPELINE_VERSION` when a change to any scoring stage (dedup/bot/topicality/sentiment/ranking) would make two posts' `base_score`/`rank_score` not directly comparable to each other.

**Schema migrations: additive-only, now an explicit rule, not just past practice.** Every migration in `supabase/migrations/` since the table-creation pair has been additive (nullable columns, no drops/renames/type changes) — but that was an unwritten convention until now. It turns out to be load-bearing, not just good hygiene: `.github/scripts/railway-deploy.sh` deploys `ingestion`→`api`→`processing` **sequentially** (each blocks up to ~10 min for Railway to resolve before the next starts) and, by the script's own documented design, **keeps deploying the remaining services even if an earlier one fails**. So on every staging/production push there's a real, routine multi-minute window where the three backend services run mismatched code, and in a failure case one can stay pinned to old code indefinitely while siblings move forward. A breaking (non-additive) schema change lands into exactly that window. The rule going forward: new columns nullable or defaulted, no drops/renames/type-narrowing in a single migration — if a column genuinely needs to go away, that's a multi-step migration across multiple deploys (add the replacement, dual-write, backfill, cut reads over, drop the old column later), not one.

**Redis format-mismatch handling.** `dedup.py`'s `deserialize_minhash` (treats undecodable or wrong-length data as "no signature," never crashes) is the template *if* any other Redis-backed module ever adopts custom binary serialization under a stable key name — `bot_filter.py`/`topicality.py` don't need this today, they use native Redis primitives (`INCR` counters, `SADD` string sets) with no equivalent format-drift risk.

**Category taxonomy.** Hand-duplicated in three independently-deployable places (`processing/src/pipeline_stages/taxonomy.py`, `api/src/types.ts`, `web/src/api/types.generated.ts`'s mirror of it) — the same Python↔TypeScript limit that keeps `Attachment`/`QuoteContent` hand-synced between `processing/`'s quote-resolution mirroring and `api/`. Deliberately **no DB `CHECK` constraint** on `processed_posts.category` — a stricter constraint would make the taxonomy harder to extend (need a migration to loosen it every time a category's added), the opposite of "easy to migrate." A new/renamed category `processing/` starts writing passes straight through `api/`'s unfiltered `/feed` response with no crash (no output schema exists); it only becomes visible-as-an-error when used as a `?category=` filter value `api/` doesn't recognize yet (correctly 400s, via the AJV `enum`). Guidance for whoever eventually builds a per-post category display in `web/`: index by the post's actual `category` value defensively (unknown value → fall back to no badge, not a crash) — nothing does this today, so it's not a live bug, but it will be the moment that feature exists.

**R2 sentiment-model registry — the reference pattern.** `processing/src/infra/model_store.py`/`training/r2_release.py`: immutable `sentiment-cnn/<version>/` artifacts plus one atomically-flippable `latest.json` pointer, resolved once per process. The one part of this system that already versioned well before this pass; extend this shape to a new integration point before inventing a different one. Done once already: the category classifier reuses this exact registry shape under a `category-classifier/` prefix, generalizing `model_store.py`/`r2_release.py` (a `--model` flag, a `prefix` constructor arg) rather than forking either.

**PWA staleness.** `web/src/components/UpdatePrompt.tsx` (new) closes a real gap: `vite.config.ts`'s `registerType: "autoUpdate"` means a new service worker self-activates and claims already-open tabs on its own — without this component, that path defaulted to an *immediate, unprompted* `window.location.reload()` the moment a new deploy's service worker took over, via `vite-plugin-pwa`'s `useRegisterSW`. Now it's a dismissable "a new version is available" banner instead, still user-triggered rather than forced. Note this intercepts `onNeedReload`, not `onNeedRefresh` — in `"autoUpdate"` mode the latter never fires (only relevant under `registerType: "prompt"`, a bigger change to service-worker lifecycle behavior this pass deliberately didn't make).

**Explicitly not done, and why:**
- A DB `CHECK` constraint on `category` — see above.
- Fixing `processing/`'s hand-mirrored copy of `api/src/attachments.ts`'s embed-parsing logic — Python↔TypeScript can't share types across that boundary; it stays hand-synced by necessity, already well-commented in both files.
- Re-architecting `railway-deploy.sh` for atomic/parallel deploys — a real, separate, larger deploy-reliability project, not a versioning-policy question. Today's additive-only schema discipline is the mitigation for the confirmed skew window, not deploy atomicity itself.
- New defensive parsing for Jetstream/Mastodon — already reasonably resilient (broad try/catch at multiple layers in `ingestion/`), and both are third-party protocols outside this project's control regardless.
- Runtime schema validation (e.g. zod) at the `api/`↔`web/` boundary — considered, deferred; see above.

## Monitoring & observability

Directly motivated by a `processing` outage that Railway's own crash alerting never caught — the restart policy kept successfully bringing the container back up, so the failure was invisible at the infra level even though `processing` was crash-looping on business logic inside an otherwise-healthy-looking container.

- **Heartbeats (Healthchecks.io)** — dead-man's-switch monitoring, 4 checks: `processing`×staging/production, `ingestion`×staging/production (deliberately 4 separate checks, not 2 shared ones — a shared check would let a healthy staging heartbeat mask a broken production one). `processing/src/infra/heartbeat.py`'s `ping()` fires once per fully successful cycle, from the very end of `main.py`'s loop — placed after `run_cycle`, `refresh_rankings`, and `cleanup_old_data` all complete without raising, and deliberately wrapped in no try/except, since an unhandled exception crashing the process before that line *is* the missed-ping signal the monitor needs to see. `ingestion/src/heartbeat.ts` is shaped differently since ingestion is event-driven, not cyclic — it pings periodically (5 min default) but only if at least one post was actually inserted since the last check, so a quiet window with zero inserts is exactly the failure it catches. Both URLs are optional env vars (`HEARTBEAT_URL_PROCESSING`, `HEARTBEAT_URL_INGESTION`, documented in `.env.example`, set per-service per-environment in Railway) — unset means no-op, never blocks startup. The Healthchecks.io account and the 4 checks themselves are non-repo state, set up manually in their dashboard.
- **Real health check** — `api/`'s `/health` does an actual `SELECT 1` against Postgres (`api/src/db.ts`'s `checkDatabaseConnection()`), bounded to a 3s timeout via `Promise.race` so an unreachable DB fails fast instead of hanging on `postgres.js`'s ~30s default `connect_timeout`. Returns 503 `{status:"error",database:"unreachable"}` on failure, `{status:"ok"}` on success. Railway's `healthcheckPath` is set to `/health` in both `api` environments — predates this change but wasn't meaningful until now, since the old handler always returned 200 regardless of DB state.
- **External uptime checks (Better Stack)** — 4 targets, non-repo: `/health` and `web/`'s root, each on staging and production.
- **Railway Observability Dashboard** — per-environment, configured in the Railway UI, non-repo.
- **Cloudflare Workers observability** — `web/wrangler.jsonc`'s `observability.enabled: true`, free request/error analytics for the deployed Worker. This is the one piece of the above that *is* in the repo.
- **Deliberately not set up**: Railway's Pro-gated resource-threshold Monitors (the free heartbeat+uptime approach already closes the gap that mattered, at zero cost) and a public status page (planned for once the app is actually public).

## Data sources

Bluesky Jetstream (public WebSocket firehose, filtered to `app.bsky.feed.post` creates) and Mastodon public timelines (polling 8 instances — `fosstodon.org`, `hachyderm.io`, `sciences.social`, `journa.host`, `universeodon.com`, `mstdn.social`, `mas.to`, `mastodon.world` — 30s interval; each chosen individually for actually having unauthenticated `/api/v1/timelines/public` access — several well-known instances, including `mastodon.social` itself, have that disabled — and for topical diversity beyond a tech-only lean). - **Upstash** — serverless Redis, REST API (not raw `redis://`). Ephemeral, TTL'd state only: LSH bands + MinHash signatures (dedup), author velocity + self-dup tracking (bot filter), entity burst counters (topicality). Postgres holds every durable result; Redis is disposable.
- **GitHub** — this repo, org `goodgorithm`. Three long-lived branches (`main` → `staging` → `production`), mirroring the Railway/Supabase environment promotion flow — see Git conventions below.
- **Healthchecks.io** — dead-man's-switch heartbeat monitoring for `processing`/`ingestion`, 4 checks. See Monitoring & observability above.
- **Better Stack** — external uptime checks on `/health` and `web/`'s root, staging + production. See Monitoring & observability above.

## Development

Each service is independent — install/run/test from within its own directory.

- **`ingestion/`, `api/`** (Node/TypeScript): `npm install`, `npm run dev` (watch mode via `tsx`), `npm run build` (type-check + compile), `npm test` (`api/` only, uses Node's built-in test runner).
- **`web/`** (Node/TypeScript, React + Vite): `npm install`, `npm run dev` (Vite dev server), `npm run build` (type-check + build, also generates the PWA manifest/service worker), `npm test` (Vitest), `npm run lint` (oxlint). Needs `VITE_API_BASE_URL` set (see `web/.env.example`) — points at a running `api/` instance.
- **`processing/`** (Python, managed with `uv`): `uv sync`, `uv run python src/main.py --once` (single cycle, for local testing) or without `--once` for the long-lived loop, `uv run pytest` (unit tests — many run without any real DB/Redis/R2 credentials, since `config.validate()` is only called explicitly from entrypoints, not at import time).
- **`training/sentiment_cnn.ipynb`**: not run locally — needs a GPU. Open in Colab or Kaggle. See the `release-sentiment-model` skill before touching this.

CI (`.github/workflows/ci.yml`) runs `processing`'s pytest suite, and builds/tests `ingestion`/`api`/`web`, on every push and PR to `main`/`staging`/`production`.

## Git conventions

- Commit messages: plain, descriptive. Include a `Co-Authored-By: Claude <noreply@anthropic.com>` trailer on commits produced by/with Claude (not required retroactively on the very first commit).
- Three long-lived branches, promoted in sequence: feature branches merge into `main` first; `main` promotes to `staging`; `staging` promotes to `production`. `staging` and `production` map directly to the matching Railway/Supabase environments — `main` itself isn't deployed anywhere, it's just the integration branch. CI runs tests/build on all three branches; pushes to `staging`/`production` additionally trigger a deploy to the matching Railway environment (per-service) once CI passes.
- Issue types (`bug`/`enhancement` labels) and the `bug/issue-#-description` / `feature/issue-#-description` branch-naming convention feeding into that `main` merge are in [`CONTRIBUTING.md`](CONTRIBUTING.md), not repeated here.
