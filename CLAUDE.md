# Goodgorithm — project context

Read this before starting work. It's the condensed reference for what this system actually does today. Deeper public-facing mechanism/policy docs live on the GitHub Wiki (see Docs at the bottom).

## What this is

An open-source, free-forever, ad-free algorithmic feed of positive/uplifting public social posts. The pitch: counter the negativity bias of mainstream platform algorithms, and reclaim "algorithm" from its usual "platform manipulating you" connotation.

**Status:** early development. `ingestion/`, `processing/`, and `api/` run on Railway; `web/` (PWA + Capacitor native) deploys to Cloudflare Workers. All four are live in both `staging` and `production`. Production: [goodgorithm.com](https://goodgorithm.com). Staging: [goodgorithm-web-staging.bandza88.workers.dev](https://goodgorithm-web-staging.bandza88.workers.dev/). Deploy/migration status changes between sessions — check actual state (`git log`, Supabase migration list, Railway deploy status) before assuming this file reflects what's currently live.

## Documentation and comment style

`CLAUDE.md`, the wiki, module docs, and inline code comments describe **current-state behavior** — what a component does, and its actual constraints and invariants — not the history of how it got that way. Explain *why* only when it's genuinely non-obvious from the code itself and a future change could get it wrong without knowing: a load-bearing constraint, a subtle invariant, a workaround for something that isn't going away. Skip incident narration, issue-number chains, and "we tried X, it didn't work, so we did Y" reasoning that doesn't change what to do next.

This also covers the quieter version of the same mistake: don't describe what a component *used to* do, lack, or get wrong before a fix — "X initially didn't have this," "an inconsistency caught after the fact," "Y was missing until this was added," or "unlike before, this now...". Write the corrected behavior as if it had always been this way. The fact that it wasn't is exactly the history that belongs in git/issues, not here — and this applies even when nothing about it looks like an "incident": a plain design gap noticed and closed in the same pass is still history, not current-state description.

History has its own home: git history and closed GitHub issues, not this file. If a durable historical log of decisions ever turns out to be worth keeping deliberately (beyond what git/issues already give you), it belongs in this repo or the wiki.

This is mostly a subtraction rule, not a rewrite mandate: most existing content here is already correct as current-state description. When editing a section, cut what's pure history and keep the genuinely load-bearing exceptions — the three constraints below are the clearest example of content that stays in full.

## Three constraints that are load-bearing, not aspirational

**1. No LLM in the algorithm itself.** Content selection (sentiment scoring, topic/newsworthiness detection, ranking) runs on classic ML: TF-IDF, spaCy NER, MinHash/LSH, a small CNN over word embeddings for sentiment. Not an LLM. The reasoning: the whole pitch is "trust why a post got selected," and classical ML is small, auditable, and doesn't drift or hallucinate the way an LLM can. This is specifically about what powers the algorithm — it does not extend to how the project is built. LLM tools (including Claude) are used openly for development, research, and docs. Don't blur this distinction in code comments, docs, or commit messages: "no LLMs in the filter," not "no LLMs anywhere."

**2. No engagement signals in ranking.** The ranking/dedup pipeline must never read likes, reposts, replies, or follower counts from the source platform. An earlier draft violated this (used an HN-style upvote-decay formula) before being caught and rewritten — a concrete reminder this constraint needs active enforcement, not just a policy statement. `processing/src/pipeline_stages/ranking.py`'s `compute_base_score` is the literal enforcement of this: `positivity(sentiment) × topicality × recency_decay × context_penalty × link_share_penalty` — every field on `RankablePost` is content-derived (sentiment, topicality, entities, recency, and the `context_penalty`/`link_share_penalty` devalue multipliers from `context_dependency.py`/`link_share.py`); none reads engagement. Bot-filtering (`bot_filter.py`) is allowed but stays defensive-only — a hard eligibility filter, never a score boost, so it can't become a backdoor engagement signal.

**3. No attention-optimization in the product.** No streaks, no "come back" push notifications, no autoplay-next, nothing engineered to maximize time-in-app. The natural extension of the other two: the product isn't just neutral about engagement, it's actively fine with not holding you, because the point is inspiring real-world action, not screen time. Unlike constraints 1 and 2, there's no single code path enforcing this today — it's a review criterion for future feature work (anti-repeat's cursor persistence, for example, is purely a "don't lose your place" convenience with no re-engagement mechanic attached), not a retrofit of something already built.

## Architecture (as built)

Five services, each independently deployable:

| Path | Language | Deployed as | What it does |
|---|---|---|---|
| `ingestion/` | TypeScript | Railway service `goodgorithm-ingestion` | Long-lived process: Bluesky Jetstream WebSocket + Mastodon polling → `raw_posts` in Postgres. |
| `processing/` | Python | Railway service `goodgorithm-processing` | Long-lived loop: content filter → dedup → bot filter → topicality → quote resolution → sentiment → base score → MMR ranking → `processed_posts`. |
| `api/` | TypeScript (Fastify) | Railway service `goodgorithm-api` | Stateless, read-only, unauthenticated HTTP — no outbound calls of its own (see Post attachments & embeds below). `/v1/feed` (cursor-paginated, ordered by `rank_score`), `/health`. |
| `web/` | TypeScript (React + Vite) | Cloudflare Workers static assets (`goodgorithm-web`, staging/production named environments) | PWA *and* Capacitor-wrapped native iOS/Android app, same codebase: infinite-scroll feed consuming `api/`'s `/v1/feed`, no accounts/personalization. `VITE_API_BASE_URL` baked in at build time (static site, no server component). |
| `training/` | Python (notebook) | Run manually on Colab/Kaggle, not deployed | Trains the sentiment CNN, exports to ONNX, publishes versioned artifacts to R2. |

Schema lives in `supabase/migrations/` (`raw_posts`, `processed_posts`, applied via Supabase's migration tooling — don't hand-edit the schema elsewhere).

**For the exact step-by-step mechanics of every pipeline stage** (thresholds, formulas, why each one works the way it does), see the published **Algorithm** page on the GitHub Wiki (see Docs at the bottom for the link) — that's the canonical, kept-current explanation. Don't duplicate it at length here; it'll drift.

### Data flow

```
Bluesky Jetstream ─┐
                    ├─> ingestion/ ─> raw_posts ─> processing/ ─> processed_posts ─> api/ ─> /v1/feed ─> web/
Mastodon polling ───┘                  (dedup, bot filter, topicality,
                                         sentiment, base score, MMR rank)
```

`raw_posts` and `processed_posts` are separate tables, joined at read time — nothing is ever mutated in `raw_posts` after ingestion, so the original data is always intact for audit/replay even as scoring logic evolves.

### Sentiment model loading

`processing/` tries once per process to load the trained CNN from R2 (`sentiment-cnn/latest.json` → versioned `model.onnx`/`vocab.json`/`config.json`); on any failure (R2 not configured, network error, missing/corrupt objects, or the loaded model's output shape not matching the hardcoded `EXPECTED_NUM_CLASSES=3`) it falls back to VADER and keeps running. `sentiment_method` on every scored post records which one actually produced that score. `util/sentiment_model.py`'s tokenizer is deliberately zero-project-imports — the training notebook fetches it standalone via a pinned commit URL — so it keeps its own copy of `text_normalize.py`'s hashtag-splitting logic rather than importing it; keep both in sync by hand if that logic ever changes. To train and publish a new model version, use the `release-sentiment-model` skill (`.claude/skills/release-sentiment-model/`) rather than improvising the R2 upload — it covers the tokenizer commit-pinning requirement and the versioned/gated-promotion release process.

### Data retention

Alpha-stage cap, not a correctness requirement: both Postgres and Redis only retain the last 24 hours of data. `processing/src/pipeline.py`'s `RETENTION_HOURS` (env-configurable, default `24`) drives a `cleanup_old_data()` step that runs every cycle, deleting `raw_posts` older than the cutoff; `processed_posts` rows cascade-delete via FK. Redis TTLs for dedup (`DEDUP_BAND_TTL_SECONDS`, `dedup.py`) and bot-filter self-dup tracking (`SELF_DUP_TTL_SECONDS`, `bot_filter.py`) are aligned to the same 24h window — no point holding LSH/dedup state for posts that no longer exist in Postgres. `pipeline.py` checks `DEDUP_BAND_TTL_SECONDS >= RETENTION_HOURS * 3600` at startup and refuses to start otherwise — dedup state expiring before its posts do would silently let real near-duplicates back into the feed.

`ranking.py`'s `RANKING_MMR_WINDOW_HOURS` (env-configurable, default `72.0`) is effectively capped at 24h by retention today (a post can't survive long enough to hit the 72h boundary) — left at `72.0` rather than lowered to match, so it becomes meaningful again automatically if retention is ever raised. Don't "fix" this mismatch without understanding why it's there first.

### Post attachments & embeds

`api/src/attachments.ts` parses each post's images, link cards, video, and quote-post content into a normalized `Attachment[]` the frontend renders — the `Attachment` union is hand-duplicated in `web/src/api/types.ts` (no shared package across the API/web boundary in this repo). Images and link cards are pure string-templating off `raw_json` (Bluesky's CDN URLs, Mastodon's own media URLs) with zero network calls at serve time.

Video follows the same pure-templating pattern: Bluesky's raw video embed only has a blob ref (CID), but the HLS playlist URL is deterministically constructable client-side as `https://video.bsky.app/watch/{did}/{videoCid}/playlist.m3u8` — no AppView call, `api/` stays untouched architecturally. Mastodon's `video`/`gifv` media are already-playable URLs. `web/`'s `VideoPlayer.tsx` uses `hls.js` as a non-Safari fallback for the `.m3u8` URLs (native `<video>` handles Mastodon's plain MP4s and Safari's native HLS directly); GIF-like video (Bluesky `presentation: "gif"`, Mastodon `gifv`) autoplays muted/looping/no-controls, regular video requires a tap.

Quote-post content resolution is the one piece that isn't pure templating — a Bluesky quote embed only ever carries `{cid, uri}`, so showing the quoted post's own text/author needs a live call to Bluesky's public, unauthenticated AppView (`app.bsky.feed.getPosts`, batched up to 25 URIs/call). This resolution happens in `processing/src/pipeline_stages/quote_resolver.py` at scoring time, not in `api/` — deliberately placed there rather than in `api/` so `api/` stays stateless/DB-in-JSON-out, and so quoted content can be run through the same `content_filter.is_content_excluded()` checks a regular post gets before it's ever stored (a quoted post carries its own moderation status independent of the post quoting it). The result is a pre-shaped, already-filtered blob on a nullable `processed_posts.quote_content` column that `api/` passes straight through with no further shaping. Deliberately never reads or stores the engagement counts (`likeCount`/`repostCount`/etc.) that `getPosts`' response includes — no engagement signals anywhere in the product, not just ranking. A quoted post absent from a successful response (deleted/blocked/detached — `getPosts` doesn't distinguish which) resolves to an explicit `not_found` status; a network/API failure just leaves `quote_content` null for that post, with no retry, since each `raw_post` is only ever scored once.

A post's own Bluesky author name/avatar needs the same kind of resolution — Jetstream's firehose carries only the author's DID, never profile data, unlike Mastodon's `raw_json` which embeds `display_name`/`avatar` for free. `processing/src/pipeline_stages/author_resolver.py` runs as its own throttled sweep (`AUTHOR_RESOLVE_INTERVAL_SECONDS`, default 60s; must run after `refresh_rankings()` in `main.py`'s loop, since its `rank_score IS NOT NULL` candidate query depends on that stage's writes from the same cycle) over `processed_posts.author_resolved_at IS NULL`, scoped to already-ranked posts only — most ingested Bluesky posts never get ranked, so resolving everything would be pure waste. Mirrors `quote_resolver.py`'s/`moderation_recheck.py`'s `getPosts` batching and per-batch failure-isolation shape. Stored on nullable `processed_posts.bluesky_author`/`author_resolved_at` — `bluesky_author` is `null` for Mastodon rows (which never need it) and for not-yet-swept or unresolvable Bluesky rows. `api/`'s `/v1/feed` coalesces `mastodon_display_name ?? bluesky_author_display_name` (same for avatar) via `api/src/author.ts`'s `buildAuthor()`.

`util/bluesky_appview.py` holds the shared `APPVIEW_BASE`/`GET_POSTS_MAX_URIS`/`APPVIEW_REQUEST_TIMEOUT_SECONDS` constants — every pipeline stage that calls Bluesky's AppView (`quote_resolver.py`, `moderation_recheck.py`, `author_resolver.py`) imports them from there rather than defining its own copy.

### Category filtering

`processing/src/pipeline_stages/category_model.py` assigns each post one of four categories: **science_technology, arts_culture, food_dining, diaries_daily_life**. The primary mechanism is a trained TF-IDF + one-vs-rest logistic regression classifier (classical ML per the no-LLM-in-the-algorithm constraint, same as the sentiment CNN), trained on a trimmed subset of `cardiffnlp/tweet_topic_multi` (HuggingFace). `taxonomy.py`'s keyword/phrase matcher is the whole-process fallback for when the classifier can't load, gated the same way `sentiment.py` falls back to VADER (`category_model.CATEGORY_METHOD`, recorded per-post on `processed_posts.category_method`). Once loaded, the trained model's output is used as-is — never second-guessed on a per-post basis, the same trust level as the sentiment CNN.

`category` is **deliberately not threaded into `ranking.py`/`RankablePost`** — a post-hoc filter on top of the existing `rank_score`, not a ranking input (same "don't accidentally create a backdoor scoring signal" discipline as the two load-bearing constraints above). `api/`'s `/v1/feed` validates `?category=` against `api/src/types.ts`'s `CATEGORIES`, but only when the param is present at all — omitting it returns the unfiltered feed, and `web/`'s `fetchFeed` client already supports passing no category through. `web/`'s `CategorySelector` renders all four categories as a no-scroll grid and never produces anything else; the unfiltered feed is reachable only via the literal `?category=all` URL value (`useCategoryParam.ts`), a deliberately hidden, unlinked feature for evaluating overall feed quality outside any category's framing, not a user-facing option.

`util/text_normalize.py`'s `split_camel_hashtags()` breaks a hashtag like `#OfCourseItsGenocide` into separate words (run before the rest of normalization, since the split depends on case boundaries that lowercasing would destroy) — every word-level stage (TF-IDF, spaCy NER, category classification) would otherwise see a hashtag as one opaque glued token. `category_model.py`/`taxonomy.py` get this for free through `normalize_text()`; `topicality.py`'s NER call site calls `split_camel_hashtags()` directly instead, since NER needs the original casing that `normalize_text()` lowercases away.

The classifier's `TfidfVectorizer` is configured with `stop_words=None` and `token_pattern=r"\b\w+\b"` — both deliberate deviations from sklearn's defaults, required for exact train/inference parity through the ONNX export. Reverting either reintroduces a token-dropping mismatch between sklearn's own tokenization and skl2onnx's exported graph that silently skews bigrams and the vector's L2 normalization. Retraining always requires re-sweeping `CONFIDENCE_THRESHOLD` from scratch rather than carrying over a previous value — the number of competing classes changes the softmax distribution's shape, so a threshold picked for one label set doesn't transfer to another. See the wiki's Categorization page for the full mechanics and the eval methodology behind the current label set and threshold.

Training/release infrastructure mirrors the sentiment CNN's exactly (`training/r2_release.py` takes a `--model {sentiment,category}` flag; `model_store.py`'s `R2ModelStore` takes a `prefix` arg) — see the `release-category-classifier` skill. Unlike the sentiment notebook, `category_classifier.ipynb` doesn't need a GPU.

### Non-English content filtering

`ingestion/`'s language filters (`bluesky.ts`'s self-reported `langs` tag, `mastodon.ts`'s server-detected `language` field) only exclude a post when a *non*-English tag is present — an absent tag is treated as English by default. `processing/src/pipeline_stages/language_filter.py` closes the gap this leaves with fastText's `lid.176` pretrained language-ID model, chosen over `lingua-py` for a meaningfully lower false-positive rate on English text at equal recall on non-English text. Runs on any post with no language tag at all, and — since Mastodon's server-reported language can be wrong at a real rate (some automated posting tools default to "English" regardless of actual content) — on every Mastodon post regardless of its tag. For a *tagged* Bluesky post it runs only in the two cases where the self-reported `langs` tag can't be trusted (`bluesky_tag_needs_recheck`): the primary `langs` value isn't English at all (`["es","en"]` gets past `ingestion/` because `en` is present somewhere in the array), or the text is predominantly non-Latin script (`is_predominantly_non_latin`, threshold `LANGUAGE_FILTER_NON_LATIN_RATIO`) — a wrong `["en"]` on Thai/CJK/Arabic text is common, and genuinely non-Latin English text doesn't occur, so this costs no real English. A Latin-script post under an `en`/`en-*` tag is still trusted as-is: `langs` is the poster's own client-set self-report, and fastText verification on short, casual Latin-script English misflags it (often at high confidence) at a rate that isn't worth the small extra recall. Runs at a tuned confidence threshold — an inconclusive read is kept, not excluded, matching `bot_filter.py`'s "don't exclude on a weak signal alone" caution. The model itself isn't committed to the repo (this project's `.gitignore` convention for ML artifacts) — fetched once per process from Meta's stable public CDN and cached locally, mirroring the pinned-third-party-artifact-URL pattern `pyproject.toml` uses for `en_core_web_sm`.

### Content moderation

Two independent hard-exclude mechanisms run in `pipeline.py`'s `run_cycle`, both checked before dedup/bot/topicality ever run so excluded content never spends that compute or gets a `processed_posts` row: the `blocked_authors` table (a manually-entered or Bluesky-bot-label-auto-inserted `(source, author_id)`, purged retroactively too) and `content_filter.is_content_excluded` (hashtag/self-label/spoiler-text/domain/sensitive-media/home-instance checks on the post itself).

**`suppressed_terms`** and **`suppressed_domains`** are both DB tables, loaded whole via `db.fetch_moderation_lists()`'s cache (refreshed at most every `MODERATION_LISTS_REFRESH_SECONDS`, default 60s, rather than on every processing cycle — see the wiki's Configuration page) so a moderator can add or remove an entry without a code change or service restart (today, by hand via the Supabase SQL editor — no admin UI/CLI; [`doc/MODERATION.md`](doc/MODERATION.md) is the edit/purge runbook, including a recurring Mastodon-instance review query). Both are deliberately narrow and hand-curated, "precision over recall": `suppressed_terms` only holds terms that function as an unambiguous adult-content self-tag (checked against post-body hashtags and Mastodon's free-text `spoiler_text` field), not identity/topic terms that merely correlate with it in some posts; `suppressed_domains` (seeded narrow, e.g. `amazon.com`/`etsy.com`) catches marketing/affiliate content that isn't self-tagged with anything at all, since it passes on its own enthusiastic sentiment — the same signal genuine positivity scores on. `content_filter.has_excluded_domain` extracts a post's link via `util/url_extract.py`'s `extract_raw_url` (shared with `dedup.py`'s near-duplicate URL extraction) and matches a listed domain exactly or as a subdomain — deliberately a separate extraction path from dedup's own, since dedup needs to reject bare-domain URLs and this check needs to match them. `quote_resolver.py`'s quoted-post filtering takes both sets the same way a regular post does.

`ADULT_LABEL_VALUES` (Bluesky's own fixed moderation-service vocabulary for adult content, `com.atproto.label.defs`) stays hardcoded, not DB-driven — it's an external protocol constant Bluesky itself defines, not something a moderator curates.

Mastodon's `sensitive` boolean (self-reported, still used by `api/src/attachments.ts` for client-side image blurring on everything the checks below don't cover) triggers a hard exclude only for the narrow combination `content_filter.has_excluded_sensitive_media` checks: `sensitive=true` AND at least one media attachment AND an empty `spoiler_text` — the one sub-case confirmed high-precision for genuine adult content. Every other `sensitive=true` combination (a `spoiler_text` present, or no media) is deliberately left blur-only, not excluded — the flag is too blunt elsewhere (movie/game spoilers, mental-health disclosure, political commentary, and courtesy content-warnings on ordinary photos all set it too) to safely hard-exclude on. Naturally always `False` for Bluesky rows, which have no `sensitive`/`media_attachments` fields in that raw shape — Bluesky's adult content is covered by its own self-label check instead.

`content_filter.has_excluded_home_instance` closes a gap the sensitive-media check can't reach: a post's own author living on a fully dedicated adult instance, with no media/spoiler-text combination on that specific post to trigger on. Distinct from `has_excluded_domain` — that matches a link *inside* the post body/card, but plenty of adult content is a native image post with no outbound link at all. Reuses `suppressed_domains` rather than a separate table (a moderator adding a domain there reasonably expects both "links to it" and "accounts hosted on it" covered) — checks Mastodon's `account.acct` field (`"user@host"` for a remote/federated account, bare `"user"` for a local one) against the list. Naturally `False` for Bluesky, which has no per-instance federation concept.

`ingestion/src/blueskyLabels.ts` is a second, separate real-time mechanism: a standing WebSocket subscription to Bluesky's own moderation-labeler stream (`com.atproto.label.subscribeLabels`), independent of the Jetstream firehose connection. On an `ADULT_LABEL_VALUES` match it retroactively deletes the already-ingested `raw_posts` row; on Bluesky's own `"bot"` account-level label it retroactively blocks the author. This exists because Bluesky's own automated image-scanning judgment on a post's actual content arrives asynchronously, later than Jetstream's post-create event, so it can never be caught by the ingestion-time/scoring-time checks above.

`ingestion/src/pendingExclusions.ts` closes a race between `bluesky.ts`'s Jetstream-driven `INSERT` and `blueskyLabels.ts`'s label-driven `DELETE` — two independent WebSocket connections with no coordination, so a label can arrive and a delete-by-source-id run before the corresponding insert has landed. A small in-memory, TTL-bounded (`BLUESKY_PENDING_EXCLUSION_TTL_MS`, default 30s) map shared between the two files: a delete that finds nothing records the `sourceId` as pending; the insert path checks it first and skips if found.

`processing/src/pipeline_stages/moderation_recheck.py` (wired as `pipeline.recheck_moderation()`) is a second, independent backstop against the same class of gap — a real-time listener with in-memory state is a single point of failure for a content-safety mechanism. Mirrors `quote_resolver.py`'s `getPosts`-batching pattern, but decoupled from ingestion time (a throttled sweep over already-scored posts, not inline in `run_cycle`). Checks both `postView.labels` (the post's own current moderation labels) and `postView.author.labels` (the author's profile-level self-label, otherwise unchecked anywhere). Tracked via `processed_posts.moderation_checked_at` so each post is swept exactly once. Throttled (`MODERATION_RECHECK_INTERVAL_SECONDS`, default 10s) since it calls an external API in batches — still comfortably beats the 30s `refresh_rankings` floor that actually gates a post becoming feed-visible.

## Performance

- `processing/src/main.py`: `refresh_rankings()`'s O(n²) MMR pass is throttled to a minimum cadence (`REFRESH_RANKINGS_INTERVAL_SECONDS`, default `30`), not run every loop iteration; the backlog-aware loop's idle sleep is `PROCESSING_BACKLOG_BUFFER_SECONDS` (default `3`).
- `processing/src/pipeline_stages/topicality.py`: spaCy loads with `parser`/`tagger`/`attribute_ruler`/`lemmatizer` all disabled — only `doc.ents` is ever read.
- `processing/src/infra/db.py`: `upsert_processed_posts`/`update_rank_scores` batch writes into chunked multi-row `INSERT`s rather than one round trip per post.
- `web/src/components/PostAttachments.tsx`: `hls.js`/`VideoPlayer` are `React.lazy`-loaded, since most posts carry no video.
- The top feed card's first image renders `loading="eager" fetchpriority="high"` (it's the usual LCP element); every other feed image stays `loading="lazy"`. A `priority` boolean threads `Feed.tsx` (`index === 0`) → `PostCard` → `PostAttachments` → `ImageGrid`/`LinkCard`, and exactly one `<img>` per card is ever boosted (`ImageGrid`'s first image wins over a `LinkCard` thumbnail).
- `web/index.html` carries a hand-authored static first-paint shell (placeholder wordmark + tagline + a skeleton feed) inside `#root`, plus an inline critical `<style>`, so a card-shaped block paints at ~TTFB instead of after the JS bundle downloads. `createRoot().render()` replaces `#root`'s children on mount. Its React-side twin is `components/FeedSkeleton.tsx` (rendered during the feed's initial `isPending`); the `<style>` block's palette tokens are copied from `src/theme.css` and its `.gg-skel-*` rules mirror `FeedSkeleton.module.css` — keep all three in sync.
- `web/index.html` also starts the default `/v1/feed` request from an inline `<script>` — before the bundle downloads — and parks the promise on `window.__feedBootstrap`; `useFeed`'s first-page `queryFn` adopts it via `src/api/feedBootstrap.ts` (`consumeFeedBootstrap`, one-shot), so the API round-trip runs in parallel with JS download/parse rather than after React mounts. The script only pre-fetches the default (no `?category=` in the URL, no fresh resume cursor); its `arts_culture` / `limit=20` / cursor-key literals are hand-synced with `useCategoryParam.ts`'s `DEFAULT_CATEGORY`, `client.ts`'s default limit, and `feedCursor.ts`'s key. `vite.config.ts`'s `prepaintOptimizations` plugin (no dependency) substitutes `__API_BASE__` → `VITE_API_BASE_URL` in dev and build, and at build time also `modulepreload`s the entry chunk, `preload`s the Latin Manrope woff2, and makes the app's own stylesheet non-render-blocking (`media="print"` swap + `<noscript>` fallback — the shell's inline `<style>` covers first paint). Runs on the Capacitor build too (harmless — it pre-warms the same request).
- Staging runs at lower intensity than production via Railway config only, no code difference: `BLUESKY_SAMPLE_RATE=0.01` (production: `0.045`), `PROCESSING_BATCH_SIZE=100`, `PROCESSING_INTERVAL_SECONDS=600`. Content-safety config (`DISABLE_LABEL_FILTER`) and Mastodon polling intensity are the same in both environments.

## Redis capacity

`processing/src/infra/redis_guard.py` checks usage once per cycle, before that cycle's dedup/bot-filter/topicality writes (`pipeline.py`'s `enforce_redis_capacity()`, called from `main.py`). Once usage crosses `REDIS_SOFT_LIMIT_RATIO` (default `0.70`) of `REDIS_MAX_BYTES` (default `1073741824` = 1GB, matching the self-hosted instance's own configured `maxmemory` in both environments), it proactively clears expendable data — `burst:entity:*` (topicality's short-lived "spiking now" signal) and `cluster:*:authors` (bot-filter's secondary self-dup signal) only. It never touches dedup's own state (`lsh:band:*`, `mh:*`, `dedup:cluster:*`) or `botvel:*` velocity tracking — losing those would let duplicate or spam content back into the feed unnoticed, a worse failure than the crash this guard exists to prevent.

`estimate_used_memory_bytes()` computes `DBSIZE × (a sampled average of real MEMORY USAGE reads across REDIS_GUARD_MEMORY_SAMPLE_SIZE keys, default 2000)`, resampled on every check rather than a hardcoded bytes-per-key constant — the key-size mix (`mh:*`'s ~700-byte MinHash signatures dominate, but `lsh:band:*`/`dedup:cluster:*`/`dedup:url:*`/`botvel:*`/`cluster:*:authors`/`tmpl:*`/`burst:entity:*` all coexist at very different sizes) can drift as traffic composition or dedup config changes. Deliberately does **not** use Redis's own `INFO memory` figure for this — untested against the self-hosted instance's own reporting, so switching to it is optional future work, not assumed here. The `MEMORY USAGE` calls for the sample are pipelined into one round trip, not one call per key.

Two different Redis TTL shapes are both in deliberate use, not an inconsistency: **fixed-window** keys (velocity, self-duplication cluster membership) set their TTL once via `EXPIRE ... NX`, never refreshed — refreshing on every hit would let a sustained duplicate/spam wave keep pushing the window forward indefinitely. **Rolling-window** keys (template-repeat counts) refresh their TTL on every hit instead — a fixed NX-only TTL here would let several continuously-active bots' counters all expire and reset on the same clock simultaneously, cycling them through a permanent "ramping back up" phase instead of ever settling above threshold for good.

`dedup.py`'s `mh:{post_id}` MinHash signatures are stored as base64 of raw `uint32` bytes, not a comma-separated decimal string (~700 bytes vs ~1.3KB). `deserialize_minhash` treats any old-format or incompatible-`NUM_PERM` data as "no signature" rather than raising — the template to follow if any other Redis-backed module's binary format ever needs to change under a stable key name (`bot_filter.py`/`topicality.py` don't need this today; they use native Redis primitives with no equivalent format-drift risk). `topicality.py`'s `burst:entity:*` key names are capped at 100 chars (`ENTITY_KEY_MAX_LEN`) — entity text comes straight from spaCy NER with no inherent bound.

## Bot filter account identity

`bot_filter.py`'s three Redis-keyed per-author signals (`bump_velocity`, `check_and_record_self_duplicate`, `bump_template_repeat`) are keyed by `bot_filter.canonical_account_id(source, author_id)`, not the raw `author_id`. Mastodon's `author_id` is `{polled_instance}/{acct}` (`ingestion/src/mastodon.ts`) — the instance we happened to poll the post from, not the account's real identity, since the same account can appear on several of the 8 polled instances' public timelines (crossposting, or simply visible via federation). `canonical_account_id` normalizes Mastodon's `acct` field to `user@host` regardless of which instance polled it: `acct` is already that form when the polled instance sees the account as remote/federated, but a bare `user` when the polled instance is the account's own home instance, so a bare form gets qualified with whichever instance polled it. Bluesky's `author_id` (a bare DID, never containing `/`) passes through unchanged — Jetstream is a single global firehose, not N independently polled instances, so it's already one identity. `dedup.py` has no equivalent author-keyed state, so no analogous bug there.

## Versioning & migration

**`api/` ↔ `web/` contract.** `api/`'s feed endpoint is versioned as `/v1/feed`; `/health` stays unversioned since it's an infra-level check (Railway's `healthcheckPath`, Better Stack's external monitor), not part of the data contract. `api/src/app.ts` registers `feedRoute` once, under `{ prefix: "/v1" }`, only.

What keeps `api/`'s and `web/`'s shapes in sync: `api/src/types.ts` is the canonical source for every response shape (`FeedPost`, `Attachment`, `QuoteContent`, `Category`, `HealthResponse`, etc.) — `web/`'s copy (`web/src/api/types.generated.ts`) is generated from it by `scripts/sync-api-types.mjs`, not hand-duplicated. This is deliberately *not* a live shared package: `api/`'s Railway service has `rootDirectory: "/api"` on the `RAILPACK` builder, and a live cross-directory dependency was genuinely uncertain to build correctly there. The generated file is committed, so neither service's build ever needs to reach outside its own directory; `.github/workflows/ci.yml`'s `web-tests` job fails if someone changes `api/src/types.ts` and forgets to run the sync script. Run it yourself after touching that file: `node scripts/sync-api-types.mjs`. There's still no runtime validation at this boundary (`web/src/api/client.ts`'s `getJson` trusts `response.json()` blindly) — the generated-types check is a compile-time guarantee only; a schema-validation library was considered and deliberately deferred, to stay consistent with `web/`'s general dependency-light bias (no router, no markdown lib, hand-rolled solutions preferred throughout).

**`pipeline_version`.** `processed_posts.pipeline_version` is written on every upsert (`processing/src/pipeline.py`'s `PIPELINE_VERSION` constant) and exposed per-post in `/v1/feed`, mirroring how `sentiment_method` records which sentiment scorer produced a score. Bump `PIPELINE_VERSION` when a change to any scoring stage (dedup/bot/topicality/sentiment/ranking) would make two posts' `base_score`/`rank_score` not directly comparable to each other.

**Schema migrations are additive-only.** Every migration in `supabase/migrations/` is additive: nullable columns, no drops/renames/type changes. This is load-bearing, not just hygiene: `.github/scripts/railway-deploy.sh` deploys `ingestion`→`api`→`processing` **sequentially** (each blocks up to ~10 min for Railway to resolve before the next starts) and keeps deploying the remaining services even if an earlier one fails. So on every staging/production push there's a real, routine multi-minute window where the three backend services run mismatched code, and in a failure case one can stay pinned to old code indefinitely while siblings move forward. A breaking (non-additive) schema change lands into exactly that window. New columns must be nullable or defaulted; no drops/renames/type-narrowing in a single migration — if a column genuinely needs to go away, that's a multi-step migration across multiple deploys (add the replacement, dual-write, backfill, cut reads over, drop the old column later), not one.

**Category taxonomy.** Hand-duplicated in three independently-deployable places (`processing/src/pipeline_stages/taxonomy.py`, `api/src/types.ts`, `web/src/api/types.generated.ts`'s mirror of it) — Python↔TypeScript can't share types across that boundary. Deliberately **no DB `CHECK` constraint** on `processed_posts.category` — a stricter constraint would make the taxonomy harder to extend, the opposite of "easy to migrate." A new/renamed category `processing/` starts writing passes straight through `api/`'s unfiltered `/v1/feed` response with no crash; it only becomes visible-as-an-error when used as a `?category=` filter value `api/` doesn't recognize yet (correctly 400s, via the AJV `enum`). Whoever eventually builds a per-post category display in `web/` should index by the post's actual `category` value defensively (unknown value → fall back to no badge, not a crash) — nothing does this today, so it's not a live bug, but it will be the moment that feature exists.

**PWA staleness.** `web/src/components/UpdatePrompt.tsx` shows a dismissable "a new version is available" banner instead of `vite-plugin-pwa`'s default behavior under `registerType: "autoUpdate"` — an unprompted `window.location.reload()` the moment a new deploy's service worker takes over. Intercepts `onNeedReload`, not `onNeedRefresh` (the latter never fires in `"autoUpdate"` mode).

**Deliberately not done:** a DB `CHECK` constraint on `category` (see above); runtime schema validation (e.g. zod) at the `api/`↔`web/` boundary (see above); atomic/parallel Railway deploys (a separate, larger deploy-reliability project — today's additive-only schema discipline is the mitigation for the confirmed deploy-skew window, not deploy atomicity itself).

## Monitoring & observability

Railway's own crash alerting doesn't catch a process that crash-loops on business logic while the container itself stays healthy — its restart policy just keeps bringing the container back up, so the failure is invisible at the infra level. The layers below exist specifically to close that gap.

- **Heartbeats (Healthchecks.io)** — dead-man's-switch monitoring, 4 checks: `processing`×staging/production, `ingestion`×staging/production (4 separate checks, not 2 shared ones, so a healthy staging heartbeat can't mask a broken production one). `processing/src/infra/heartbeat.py`'s `ping()` fires once per fully successful cycle, from the very end of `main.py`'s loop — placed after `run_cycle`, `refresh_rankings`, and `cleanup_old_data` all complete without raising, and deliberately wrapped in no try/except, since an unhandled exception crashing the process before that line *is* the missed-ping signal the monitor needs to see. `ingestion/src/heartbeat.ts` is shaped differently since ingestion is event-driven, not cyclic — it pings periodically (5 min default) but only if at least one post was actually inserted since the last check, so a quiet window with zero inserts is exactly the failure it catches. Both URLs are optional env vars (`HEARTBEAT_URL_PROCESSING`, `HEARTBEAT_URL_INGESTION`) — unset means no-op, never blocks startup. The Healthchecks.io account and the 4 checks themselves are non-repo state, set up manually in their dashboard.
- **Real health check** — `api/`'s `/health` does an actual `SELECT 1` against Postgres (`api/src/db.ts`'s `checkDatabaseConnection()`), bounded to a timeout (`HEALTH_CHECK_TIMEOUT_MS`, default 3s) via the shared `withTimeout()` helper so an unreachable DB fails fast instead of hanging on `postgres.js`'s ~30s default `connect_timeout`. Returns 503 with `{status:"error", database:{reachable:false, latency_ms, error}}` on failure, 200 with `{status:"ok", database:{reachable:true, latency_ms}}` on success — the real error (timeout vs. connection-refused vs. auth failure) is preserved and logged. Railway's `healthcheckPath` is set to `/health` in both `api` environments. `processing/` and `ingestion/` have their own equivalent `GET /health` status endpoints — see Service resilience below.
- **External uptime checks (Better Stack)** — non-repo. `api/`'s `/health` and `web/`'s root, each on staging and production. Plus two **production-only** checks on `processing/`'s and `ingestion/`'s `GET /health/strict` (see Service resilience below), which returns `503` when that service reports `status: "degraded"` — so a degraded-but-running backend service, previously watched by nothing, now pages. Each also asserts the body contains `"status":"ok"` (the two `/health` bodies are serialized identically for this). Debounced: checked every ~3 min, alert after 2 consecutive failures.
- **Railway Observability Dashboard** — per-environment, configured in the Railway UI, non-repo.
- **Cloudflare Workers observability** — `web/wrangler.jsonc`'s `observability.enabled: true`, free request/error analytics for the deployed Worker. This is the one piece of the above that *is* in the repo.
- **Deliberately not set up**: Railway's Pro-gated resource-threshold Monitors (the free heartbeat+uptime approach already closes the gap that mattered, at zero cost) and a public status page (planned for once the app is actually public).

## Service resilience

Guiding principle: if a service can continue operating at reduced quality when one external dependency degrades, it should — a crash is reserved for failures that make continuing genuinely pointless, not one stage hiccuping.

- **`processing/`'s Redis calls degrade instead of crashing.** `dedup.py`/`bot_filter.py`/`topicality.py`'s Redis-writing methods each catch and degrade to a documented safe default rather than propagating — see the wiki's Deduplication / Bot Filter / Topicality pages for what each one degrades to and why the three directions genuinely differ (dedup accepts a real, visible cost; bot_filter biases toward false negatives, never false positives on real users; topicality's degrade is a pure ranking-input weakening with no false signal either way).
- **`processing/`'s Postgres calls deliberately still crash.** `infra/db.py` has no try/except anywhere — unlike Redis, a Postgres write *is* the actual deliverable of most stages, so silently swallowing a write failure would be more deceptive (a cycle claiming success while doing nothing) than the crash it produces today. A deliberate choice, not an oversight.
- **`infra/heartbeat.py`'s ping is a pure alive/dead signal** — it's what makes the dead-man's-switch monitoring above work. `infra/degradation.py` is the separate "alive but degraded" signal: in-memory, process-local state recording what degraded and when, read by `processing/`'s status endpoint (below).
- **Every backend service has a `GET /health`.** `processing/` and `ingestion/` each run a minimal HTTP server for just this one route (Python's built-in `http.server`, Node's built-in `http` module respectively — neither warrants a new framework dependency for a single static route). Each reports an auditable first-look snapshot: current degradation state, which model versions `processing/` actually has loaded (`sentiment.py`/`category_model.py`'s resolved R2 version strings), per-connection state for `ingestion/`'s Bluesky/Mastodon sources, and public/safe config values (thresholds, intervals, pool sizes — never credentials or the heartbeat ping URLs themselves, which are unguessable bearer-token-style URLs). This is explicitly a fast first signal, not a replacement for logs. `/health` always returns `200` (it's Railway's deploy-time `healthcheckPath` for these two services — a deliberately-still-running degraded process must not fail its deploy). A sibling `GET /health/strict` returns the same body with `503` when `status: "degraded"`, so an external monitor can alert on degradation without body parsing — **monitoring-only, never wire it to `healthcheckPath`**. For `processing/`, `status` also flips to `"degraded"` (with a synthetic `degraded.cycle` entry) when the last fully-successful cycle is older than `STATUS_STALE_CYCLE_SECONDS` (default 900) — a loop that wedged without crashing. The two services' `/health` bodies are serialized byte-compatibly (compact JSON) so one monitor keyword assertion covers both.
- **`ingestion/` has a global `unhandledRejection`/`uncaughtException` backstop** (`index.ts`) — today's coverage is complete by discipline (every real call site in `bluesky.ts`/`blueskyLabels.ts`/`mastodon.ts` already has a local try/catch), not by a safety net; this catches a future gap and crashes loudly with a clear log line rather than however Node's own default rendering would.
- **`ingestion/`'s heartbeat paging condition stays as-is** — it fires if *either* Bluesky or Mastodon has inserted since the last check, so a fully-dead single source is invisible to it. The per-source state on `ingestion/`'s `/health` closes the visibility gap without touching what actually pages, since making the page condition stricter is a separate, bigger decision.

## Visual identity

Settled through several rounds of live iteration (component mockups in both themes, not abstract swatches). Concepts ruled out along the way, worth not re-proposing: an open-arc icon that read as a loading spinner, an uppercase-G that read as a power/off glyph, a two-g composition that was too busy.

**Implemented in `web/`.** `src/theme.css` holds the palette as CSS custom properties (light values on `:root`, dark values under `prefers-color-scheme: dark` — no manual toggle exists), which every CSS Module references instead of hardcoded literals. Manrope is self-hosted via `@fontsource-variable/manrope` (not a CDN call, so the woff2s get precached by the PWA's service worker like every other build asset). `Logo.tsx`/`Wordmark.tsx` render the mark/wordmark from the spec below; `App.tsx`'s header uses `Wordmark` in place of a plain-text heading. **Flagged to be reviewed once more, fresh, before v1 ships** — implementation doesn't resolve that flag, which is about confidence in the design itself, not whether it's wired up.

## Data sources

Bluesky Jetstream (public WebSocket firehose, filtered to `app.bsky.feed.post` creates) and Mastodon public timelines (polling 8 instances — `fosstodon.org`, `hachyderm.io`, `sciences.social`, `journa.host`, `universeodon.com`, `mstdn.social`, `mas.to`, `mastodon.world` — 30s interval; each chosen individually for actually having unauthenticated `/api/v1/timelines/public` access — several well-known instances, including `mastodon.social` itself, have that disabled — and for topical diversity beyond a tech-only lean). ## Development

Each service is independent — install/run/test from within its own directory. None of this covers getting a local Postgres/Redis running or wiring `.env`s between services — see the wiki's [Local Development](https://github.com/goodgorithm/goodgorithm/wiki/Local-Development) page for that, or the `local-dev-setup` skill for an interactive walkthrough of the same steps.

- **`ingestion/`, `api/`** (Node/TypeScript): `npm install`, `npm run dev` (watch mode via `tsx`), `npm run build` (type-check + compile), `npm test` (both services, Node's built-in test runner).
- **`web/`** (Node/TypeScript, React + Vite): `npm install`, `npm run dev` (Vite dev server), `npm run build` (type-check + build, also generates the PWA manifest/service worker), `npm test` (Vitest), `npm run lint` (oxlint), `npm run test:e2e` (Playwright, Chromium/Firefox/WebKit — see CONTRIBUTING.md; a documented pre-push/pre-merge check, not a CI gate). Needs `VITE_API_BASE_URL` set (see `web/.env.example`) — points at a running `api/` instance.
- **`processing/`** (Python, managed with `uv`): `uv sync`, `uv run python src/main.py --once` (single cycle, for local testing) or without `--once` for the long-lived loop, `uv run pytest` (unit tests — many run without any real DB/Redis/R2 credentials, since `config.validate()` is only called explicitly from entrypoints, not at import time).
- **`training/sentiment_cnn.ipynb`**: not run locally — needs a GPU. Open in Colab or Kaggle. See the `release-sentiment-model` skill before touching this.

CI (`.github/workflows/ci.yml`) runs `processing`'s pytest suite, and builds/tests `ingestion`/`api`/`web`, on every push and PR to `main`/`staging`/`production`.

## Git conventions

- Commit messages: plain, descriptive. Include a `Co-Authored-By: Claude <noreply@anthropic.com>` trailer on commits produced by/with Claude.
- Three long-lived branches, promoted in sequence: feature branches merge into `main` first; `main` promotes to `staging`; `staging` promotes to `production`. `staging` and `production` map directly to the matching Railway/Supabase environments — `main` itself isn't deployed anywhere, it's just the integration branch.
